# Семинар 1 ноября: действующая интеграция PayKeeper

Страница: https://tsiframir.ru/forums/2026-nizhny-novgorod/
Магазин: https://tsiframir.server.paykeeper.ru — существующий, с реальными успешными оплатами. `/api/paykeeper/config` отвечает 410 из-за закрытого июньского форума, не из-за недоступности провайдера.

## Реализация

Новый checkout использует JSON API счетов того же магазина. В долговременном реестре PayKeeper до перехода покупателя сохраняются order ID, событие, тариф, полная сумма, имя/email/необязательный телефон, время, срок и статус. Новая база, магазин, CRM и передача клиентом редактируемой суммы провайдеру не нужны.

- `GET /api/seminar-quote`: серверное время, Europe/Moscow с явными +03:00, no-store. 1600 ₽ до 26 октября 00:00; 1800 ₽ до 1 ноября 00:00; 2000 ₽ до 1 ноября 18:00. Live начинается в 12:00, новые заказы запрещены с 18:00.
- `POST /api/seminar-checkout`: проверяет форму, согласие, событие, salesOpen и принятую цену. Клиент не может передать сумму, тариф, invoice/order ID. Смена цены требует отдельного подтверждающего нажатия. UUID order ID `TSMNN-20261101-{TARIFF}-{UUID}` генерируется сервером.
- `/change/invoice/preview/`: сервер передаёт сумму, корзину, контакт, custom_data с event/tariff/quantity, проверенный return URL и `expiry=min(now+15min, следующая граница, 18:00)`. Preview создаёт счёт без отправки письма со счётом. Часовая зона кабинета подтверждена как московская по created/expiry полям.
- Браузер получает только фиксированную ссылку `/bill/{invoiceId}`, order ID, сумму, количество и HMAC-SHA256 токен статуса. Ни секретов, ни контактов, ни редактируемой корзины в navigation URL нет. Токен сохраняется в sessionStorage исходного apex/www origin; return URL сохраняет тот же разрешённый origin.
- `POST /api/seminar-status`: проверяет HMAC до запроса `/info/invoice/byid/`, затем invoice ID, order ID, точную сумму и срок. Только authenticated `status=paid` с payment ID и временем оплаты подтверждает оплату. URL paid=1, redirect, клиентские данные и GET не подтверждают её. Ответ не содержит контактов. Токен не истекает вместе со счётом, поэтому поздняя проверка допустима; повтор не создаёт билеты/письма.
- Подтверждение содержит номер заказа, одного участника, сумму, название, 1 ноября 2026, 12:00–18:00 МСК, Маринс Парк Отель, ул. Советская, 12. Pending/ошибка явно не обещают оплату. После закрытия вкладки токен может потеряться; квитанция/заказ PayKeeper и организатор остаются штатным способом найти платёж.

## Доступ и сохранность магазина

Создан пользователь интеграции id 6 в том же магазине: admin=false, refund=0, invoices_only=true. Старые пользователи id 1, 2, 5 и все глобальные настройки оставлены прежними. В encrypted production ENV существующего Vercel project добавлены `PAYKEEPER_API_LOGIN` и `PAYKEEPER_API_PASSWORD`; используются прежние `PAYKEEPER_SERVER_URL`, `PAYKEEPER_SECRET`. Значения не записаны в репозиторий/отчёты/логи; браузерная cookie не является production credential.

Merchant informer остаётся email. Магазин не переключён на POST, прежние уведомления сохранены. Существующий `/api/paykeeper/callback` сохраняет MD5/order/amount проверку и идемпотентный ACK, но магазин не вызывает его для нового invoice. Авторитетный источник подтверждения семинара — API реестра PayKeeper при возврате, возвращении во вкладку или нажатии проверки. Это API polling, а не callback; требование исходного задания о доставленном проверенном callback не подтверждено. Поздняя доставка merchant email не меняет статус оплаты.

Сохранённый в этой вкладке заказ блокирует создание второго и сохраняет исходный токен статуса. Истёкший счёт не побуждает платить повторно: начатая банковская попытка может ещё завершиться, поэтому предлагается повторная проверка или обращение к организатору. Для ещё одного билета также предлагается связаться с организатором. Ограничение вкладки предотвращает случайную повторную покупку в этом сценарии, но не является межустройственным реестром дублей.

Организатор видит счета, оплаты и экспорт в защищённом кабинете; семинар выделяется префиксом order ID и услугой. Посетители не публикуются. Отдельное письмо-билет от сайта не обещается. Существующие email/фискальные уведомления настроены у провайдера; фактическая доставка нового чека без платежа не проверена. Корзина наследует действующий tax='none', одну позицию и полную стоимость; реквизиты и касса остаются действующими. Это не полное фискальное E2E нового продукта.

## Проверенный срок и оставшийся вопрос

Счёт 20261013205736625 создан 13 октября в 20:57:36 МСК, expiry 20:58:21 МСК. После срока API показал expired, новый вход /bill/ не переводил в банк. Уже открытая банковская страница показывала ещё 12 секунд. Карта не вводилась, списание не выполнялось: таймер не доказывает возможность позднего списания или минимум карточного TTL.

В доступных merchant settings не найдено invoice-level expirationDate/sessionTimeoutSecs. PayKeeper документирует ограничение перехода; точный запрет списания после expiry через открытую банковскую страницу/3DS/QR не описан. Альфа-Банк поддерживает expirationDate и отмену, но проброс через PayKeeper invoice API не документирован. Отказ callback после списания не заменяет защиту. Молча закрывать продажи до 18:00 нельзя.

Исходный строгий режим сохранён: новая оплата выключена. Публичная форма недоступна, не создаёт заказ и показывает «Онлайн-оплата временно недоступна» с действующим контактом. Статус ранее созданного заказа проверяется независимо от gate и даты.

Для включения требуется одно из двух:
1. Гарантия/настройка PayKeeper точного запрета списания при t >= expiry для всех уже начатых попыток карты и СБП; после проверки — актуальный review и выпуск соответствующей конфигурации.
2. Явное изменение владельцем правила: разрешить завершение уже начатой банковской оплаты по цене счёта после границы. Только после этого в существующем Vercel project разрешено установить `PAYKEEPER_SEMINAR_ALLOW_STARTED_PAYMENT_COMPLETION=true` и выпустить ту же проверенную реализацию. По умолчанию флага нет; наличие API-доступа или истечение времени ожидания не считается разрешением. Новые счета в любом режиме создаются по текущей серверной цене и запрещены с 18:00.

Нет необходимости покупать API, создавать новую БД или передавать секреты в чат. До решения владельца флаг не включён.

## Проверки и выпуск

Команды: `npm test`, `npm run build`, `npm run test:browser`. Lint/typecheck scripts отсутствуют. Проверяются тарифы/границы/12:00/18:00, stale consent, часы браузера, tampering, HMAC и binding реестра, поздний/повторный статус, неподтверждённый success, redirect, ошибки, keyboard и 375/768/1440.

Unit/browser mock не являются платёжным E2E. Живой no-charge contract-check нового адаптера проверяет invoice, server status и банковский переход; тестовый счёт затем отзывается. Успешное/неуспешное денежное sandbox E2E не выполнено: исторические TestPayments/TestgwSBP сейчас не включены. Реальные списания не разрешены и не проводились.
