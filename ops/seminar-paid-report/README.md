# Ежедневные подтверждённые оплаты семинара

Изолированная автоматизация для `seminar-2026-nizhny-novgorod`, 1 ноября 2026.
Сайт, формы, цены, счета и остальные рассылки не изменяются. Python 3.9+,
стандартная библиотека. Отправка разрешена только двум проверенным получателям.

## Состояние доступа на 22 октября 2026

Текущая интеграционная учётная запись PayKeeper имеет доступ только к счетам.
`/info/payments/bydatecount/` и `/info/payments/bydate/` отвечают HTTP 200 с
`error_code: 312`, «Действие доступно только администраторам».
Автоматизация останавливается с `PAYKEEPER_READ_PERMISSION_REQUIRED`.
Нулевой отчёт в этом случае не создаётся и не отправляется.
До предоставления существующего подходящего доступа timer должен оставаться
disabled/inactive; реальный тест отправлять нельзя. Не менять роль существующего
пользователя, не создавать счета, платежи, возвраты или новые Green API instances.

## Учёт и границы среза

Заказ идентифицируется точным UUID orderid семинара, дополнительно проверяется
eventId в метаданных оплаченного счёта и его paymentid. Телефон/email не участвуют
в объединении. Три исторических синтетических orderid исключены явно, тестовые
платёжные системы исключены по проверенному полю is_test текущего merchant API.
Если поле исчезло или изменило тип, расчёт прекращается.

Платежи перечисляются для всех систем и всех девяти документированных статусов
с from/limit, независимой проверкой fullcount до и после чтения, обнаружением
повторяющихся ID. Если count равен нулю, повторяется count: merchant invoice API
возвращает пустой не-JSON body для пустого списка. Ошибка API никогда не заменяется
нулём. Диапазон — с 2026-01-01 до следующего дня; это включает все заказы данного
семинара, регистрация которого появилась в октябре 2026. Другие события исключены.

Фактическое время оплаты — obtain_datetime, а не создание счёта и не
success_datetime (уведомление магазина). Часовой пояс merchant API — Europe/Moscow,
как в существующей интеграции. Все суммы считаются целыми копейками. Для каждого
целевого платежа читается полный refunds/bypaymentid; только status=done учитывается
по datetime. Сумма всех подтверждённых возвратов обязана совпасть с refund_amount.
Неизвестные статусы, даты, суммы, пропавшие платежи и расхождение реестров блокируют
отправку. Полученные, успешно подтверждённые, stuck и возвратные оплаченные статусы
учитываются; pending/failed/canceled исключены.

Ежедневный срез фиксирован в 19:00 МСК. Поступления/возвраты после него не меняют
отчёт, даже при позднем запуске. «Всего оплаченных» — уникальные orderid с остатком
больше нуля на срез; полностью возвращённые исключены также из сегодняшнего числа.
«Сегодня» — фактические оплаты 00:00–19:00 МСК. Поступления и возвраты показаны
отдельно; дневное сальдо может быть отрицательным при возврате старого платежа.
Тест явно помечен и использует текущий момент вместо 19:00. Нулевые дни отправляются.

## Production пути и запуск

- Код: `/opt/tsiframir-site/reports/releases/<reviewed-git-sha>/`;
  `/opt/tsiframir-site/reports/current` указывает на immutable reviewed release.
- Units: `/etc/systemd/system/tsiframir-paid-report.{service,timer}`.
- Отдельные секреты: `/etc/tsiframir-site/paid-report.env`, root:root, 0600.
  systemd читает их до запуска от непривилегированного пользователя `tsiframir-site`.
- Состояние: `/var/lib/tsiframir-paid-report/report.sqlite3`, каталог 0700;
  lock: `/var/lib/tsiframir-paid-report/report.lock` (kernel flock).
- Журнал: `journalctl -u tsiframir-paid-report.service`; только агрегаты,
  маски получателей, provider message IDs и фиксированные коды ошибок.

Обязательные ключи отдельного EnvironmentFile (значения не хранить в Git):
`PAYKEEPER_SERVER_URL`, `PAYKEEPER_API_LOGIN`, `PAYKEEPER_API_PASSWORD`,
`GREEN_API_URL`, `GREEN_API_INSTANCE_ID`, `GREEN_API_TOKEN`,
`REPORT_OWNER_CHAT_ID`, `REPORT_SERGEY_CHAT_ID`,
`REPORT_EXISTING_CHATS_VERIFIED=1`, `REPORT_START_DATE=YYYY-MM-DD`.
Флаг существующих чатов выставляется только после проверки исходных получателей
и истории текущего бесплатного instance; не подключать третий чат. Публичный API
не раскрывает текущий план/остаток квоты; тариф и фактический расход подтверждаются
в кабинете владельца, без изменения тарифа. Бесплатный Developer имеет три чата
в месяц; оба существующих чата уже использовались в октябре 2026.

Порядок активации после независимого review exact commit:

1. Установить immutable код и units, сохранить существующий app current.
2. Записать отдельный root-only EnvironmentFile; проверить доступ к платежам,
   счетам и подтверждённым возвратам. `--mode dry-run` только читает API.
3. Сверить dry-run с кабинетом, проверить authorized и существующие два чата/квоту.
4. Один запуск `--mode send-test` с тем же EnvironmentFile и StateDirectory.
   Проверить по обоим idMessage точный текст и status sent/delivered/read.
5. Только после успешных проверок выполнить
   `systemctl enable --now tsiframir-paid-report.timer`.
   Проверить `systemctl list-timers tsiframir-paid-report.timer`.

OnCalendar явно использует Europe/Moscow при любом системном TZ. Persistent=true
переживает reboot: при пропуске запуска выдаёт последний завершённый срез 19:00,
не старше REPORT_START_DATE; все пропущенные дни пачкой не рассылаются.
Три запуска service максимум за 10 минут; безопасные чтения повторяются до трёх раз.
Snapshot сохраняется один раз на дату и используется обоими получателями.

## Защита от повторных сообщений

SQLite synchronous=FULL фиксирует claim отдельно для каждого получателя до POST.
Подтверждённый ответ сохраняет idMessage; последующие запуски только проверяют
getMessage, не отправляют повторно. Состояние переживает restart и reboot.
Неопределённый ответ, timeout, crash после claim или отказ сервера блокирует повтор
POST для данного получателя. Это намеренно допускает пропуск вместо дубля.
Сбой у первого получателя не мешает второму получить подтверждённый снимок.
Тест имеет постоянный ключ test-v1 и автоматически второй раз не отправляется.

При uncertain проверить журнал Green API вручную по получателю, тексту и времени,
найти idMessage и сверить сообщение. Не удалять SQLite, не менять ключи/получателей
для обхода блокировки. Любое исправление состояния требует подтверждённых данных
о результате предыдущей отправки. Green 200/idMessage означает принятие; окончательный
успех определяется чтением точного сообщения со статусом sent/delivered/read.
