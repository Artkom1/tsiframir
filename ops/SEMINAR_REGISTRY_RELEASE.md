## Хранение и доступ организатора

Источник истины — существующий durable invoice ledger PayKeeper. POST `/api/seminar-checkout` сохраняет имя (`clientid`), телефон (`client_phone`), email (`client_email`), уникальный UUID заказа (`orderid`), сумму (`pay_amount`) и `service_name.custom_data.codeWord` вместе с `eventId`, `tariff`, `quantity` при создании счёта до оплаты. API PayKeeper возвращает custom_data как заключительный JSON-сегмент `;PKDC|…|` в `service_name`. Время регистрации — `created_datetime`. Оплата обновляет тот же счёт: `status`, `paymentid`, `paid_datetime`. Повторные callbacks только подтверждаются существующим обработчиком; новый заказ с тем же email получает другой UUID. Локальной базы, дублирующего поля или миграции нет.

Код сохраняется дословно, включая пробелы и регистр (это заменяет прежнее trim-поведение, описанное в отчёте 16 октября). Старые уже сохранённые значения восстановить до trim невозможно. Пустой код допустим. Поиск использует trim/casefold, не заменяет кириллицу латиницей. Код не влияет на цену. Тарифы и границы продаж по Москве не изменены: 1600 до 25 октября включительно, 1800 с 26 по 31 октября, 3000 с 1 ноября до прежнего закрытия продаж в 15:00.

Открыть **https://tsiframir.ru/organizer/seminar-orders** по HTTPS, в запросе браузера ввести действующие логин и пароль PayKeeper организатора, которые уже настроены для интеграции сайта. Никакого нового пароля не создаётся и существующие credentials не публикуются. Если организатору эти данные недоступны, владелец должен предоставить доступ через свой безопасный процесс; выдавать серверный секрет из отчёта нельзя. При десяти неверных попытках действует минутная блокировка IP. Для завершения доступа на общем компьютере закрыть приватное окно браузера, поскольку HTTP Basic хранится браузером.

В таблице доступны контакты, исходный код, регистрация, сумма и статус оплаты, IDs и срок счёта. Поле кода ищет полное слово или часть без учёта регистра. «Наличие кода» выбирает все/с кодом/без кода; флажок «Только оплаченные» ограничивает оплаченные. «Показать» применяет фильтры, «Скачать CSV для Excel» выгружает те же условия и все 15 полей. Для полной выгрузки нажать «Сбросить», затем CSV. CSV UTF-8 с BOM и `;`; потенциальные Excel-формулы защищены текстовым апострофом, исходное значение в PayKeeper не меняется. Таблица прокручивается по горизонтали на телефоне.

Запрос `/info/invoice/search/?query=TSMNN-20261101-*&start_date=2026-01-01&end_date=2027-01-01` включает созданные, отправленные, оплаченные и истёкшие счета. `/info/invoice/list/` здесь не используется: он исключает `created`. У search нет документированной пагинации. Проверяются точный UUID-префикс события и eventId метаданных; противоречивые данные приводят к закрытой ошибке 503. При недоступности PayKeeper реестр также отвечает 503, не показывает устаревшую копию.

## Защита и выпуск

UI и CSV используют одну авторизацию с timing-safe сравнением, ограничением неверных входов, private/no-store, noindex, CSP, запретом iframe и cross-site запросов. Фильтры передаются POST, чтобы код не попадал в URL и access log. HTML экранирован. CSV не содержит URL оплаты или подписанных токенов. Credentials остаются в существующем root-owned env0600. Nginx заменяет X-Forwarded-For; процесс принимает только loopback8093. Не менять приложение, Telegram, nginx, env или банк.

Обязательны ранний независимый Astra xhigh review, scoped checks, затем чистый commit, свежий независимый финальный/security/release review точного commit и один полный gate `npm test`, `npm run test:browser` с production build, exact-commit archive и проверка сохранности. Продакшен: push проверенной ветки, проверка архива, новый root-owned release, atomic symlink и restart только сайта; при провале health/quote откат на базу. Проверить manifest, nginx/config/env/app и исходный dirty checkout до/после.

Платёжный lifecycle проверяется синтетическим provider fixture: создание с кодом/без, pending→paid в той же записи, повторные подписанные callbacks, повторный read/reload, один email с разными UUID, фильтры, CSV, отказ неавторизованным. В production разрешена безопасная проверка двух новых синтетических неоплаченных счетов с последующим revoke только этих счетов. Не отправлять счёт клиенту, не открывать банковскую сессию, не отмечать оплачено, не списывать деньги. Реальный paid settlement без банковского платежа не проверяется.
